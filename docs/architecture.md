## 1. Назначение документа

Этот документ определяет архитектуру приложения: основные подсистемы, модели данных, потоки данных, зависимости между компонентами, владение состоянием и правила выполнения длительных операций.

Документ является источником истины для архитектурных решений проекта.

Функциональные требования и требуемое поведение пользователя определяются в `requirements.md`.

Конкретные математические методы:

- выделения границ;
- fitting;
- сегментации;
- фильтрации выбросов;
- группировки отверстий;
- оптимизации геометрии;

определяются в `algorithms.md`.

Архитектура не должна зависеть от конкретной структуры классов сильнее, чем это необходимо. Обычный рефакторинг классов и файлов не должен требовать изменения этого документа, если архитектурные границы и контракты сохраняются.

## 2. Архитектурные цели

Архитектура определяется следующими основными ограничениями проекта:

1. Исходные облака могут занимать несколько гигабайт и содержать миллионы и более точек.
2. Исходное облако не должно загружаться целиком в оперативную память.
3. Целевой компьютер может иметь слабый CPU, небольшой объём RAM, HDD и не иметь дискретной GPU.
4. Исходный файл может находиться на медленном сетевом ресурсе.
5. Текстовый `.asc/.xyz` после первоначального импорта не должен постоянно перечитываться.
6. Первый этап обработки работает по фиксированной density map.
7. Второй этап работает по реальным измеренным точкам.
8. Трудоёмкие операции запускаются только явно пользователем.
9. Изменение входов внутри этапа может оставить неприменённые изменения без автоматического пересчёта. Изменение rough-входов после начала precise-stage требует подтверждённого полного сброса второго этапа без Undo.
10. Пользователь должен иметь возможность закрыть программу и продолжить работу позже.
11. Ручная fixed geometry второго этапа имеет приоритет над автоматическим fitting.
12. Финальная геометрия должна состоять из CAD-примитивов и быть пригодна для дальнейшего редактирования.
13. Контуры должны оставаться топологически непрерывными.
14. Автоматически построенная точная геометрия должна соблюдать односторонний допуск в сторону сохранения материала.
15. Пользовательские требования к desktop GUI, UX и русскому языку интерфейса определены в [requirements.md, §2.1](requirements.md#21-пользовательский-интерфейс).

## 6. Два этапа обработки

Архитектура должна строго различать rough stage и precise stage.

### 6.1. Rough stage

Источник данных:

```text
Density PNG
```

Назначение:

- выбор детали;
- приблизительный внешний контур;
- приблизительные отверстия;
- группировка отверстий;
- внутренние вырезы;
- ручная корректировка;
- подготовка областей для выборки исходных точек.

Rough geometry является приближённым рабочим описанием и не считается финальной точной CAD-геометрией.

Внешний rough-контур допускается представлять редактируемой полилинией.

### 6.2. Precise stage

Источник данных:

```text
Reduced Point Cloud
```

Полученный из реальных измеренных точек persistent point cache.

Назначение:

- точное восстановление внешней границы;
- уточнение отверстий;
- уточнение внутренних вырезов;
- построение CAD-примитивов;
- обеспечение непрерывности;
- контроль допуска;
- минимизация разумного количества CAD-объектов.

Rough geometry используется как начальная информация и средство выбора соответствующих реальных точек. Явный Build Reduced Point Cloud принимает текущий rough-state для перехода; отдельное Confirmed Rough Geometry не требуется.

При изменении rough-входов после начала precise-stage действует подтверждённый полный сброс по [requirements.md, §21](requirements.md#21-переходы-между-этапами). Сбрасываются reduced cloud с удалениями точек, precise geometry с ручными изменениями и Fixed states, fitting/optimization results и прочие зависимые данные второго этапа. Отказ от подтверждения сохраняет состояние; подтверждённый сброс не поддерживает Undo и не оставляет старый precise-stage как Outdated.

## 7. Логические подсистемы

Application layer.

Отвечает за координацию пользовательских сценариев и явных операций:

ImportPointCloud

FindRoughHoles

Application layer связывает GUI, domain model и вычислительные подсистемы.

Он не должен содержать реализацию математических алгоритмов.

### 7.2. `ui`

Presentation layer:

- QML;
- Qt Quick Controls;
- графический canvas;
- свойства объектов;
- управление selection;
- zoom/pan;
- отображение progress/error/state.

`ui` не является владельцем геометрии проекта и не выполняет тяжёлые вычисления.

### 7.3. `project`

Хранит логическое состояние открытого проекта и отвечает за:

- состояние этапов;
- параметры обработки;
- ссылки на project-owned data;
- сериализацию;
- загрузку;
- autosave;
- recovery;
- актуальность результатов.

### 7.4. `io`

Отвечает за:

- потоковое чтение ASC/XYZ;
- базовые файловые операции;
- проверку входного формата;
- файловые ошибки.

### 7.5. `cache`

Отвечает за:

- создание persistent point cache;
- открытие существующего cache;
- проверку совместимости;
- пространственный доступ;
- чтение необходимых областей;
- metadata cache.

### 7.6. `raster`

Отвечает за операции первого этапа:

- построение density map;
- raster analysis;
- поиск rough-геометрии;
- работу с PNG.

OpenCV должен быть в основном локализован в этой подсистеме.

### 7.7. `geometry`

Содержит независимую от GUI геометрическую модель:

- точки;
- контуры;
- линии;
- дуги;
- окружности;
- связи между элементами;
- topology;
- constraints.

### 7.8. `pointcloud`

Отвечает за второй этап:

- reduced point cloud;
- выборку реальных точек;
- работу с edited reduced cloud;
- точное восстановление геометрии;
- пространственные запросы по рабочему облаку.

### 7.9. `export`

Преобразует финальную domain geometry во внешние форматы.

Первоначально поддерживается DXF.

## 8. Правила зависимостей

Должны соблюдаться следующие ограничения:

```text
geometry    не зависит от ui
io          не зависит от ui
cache       не зависит от ui
raster      не хранит domain state в QML
pointcloud  не хранит domain state в QML
export      не читает геометрию из UI
```

GUI может зависеть от application/domain API.

Domain model не должна зависеть от конкретных QML-компонентов.

Геометрический объект не должен существовать только как visual item.

Например, окружность является объектом domain model, а QML/renderer только отображает её.

## 9. Состояние проекта

Приложение должно иметь единую логическую модель открытого проекта.

Жизненный цикл различает:

- приложение без открытого проекта;
- выполняемый импорт с ещё не принятым результатом, при необходимости одновременно с текущим открытым проектом;
- полноценный открытый проект, созданный только после успешного импорта;
- ранее сохранённый проект, открытый в частично доступном состоянии из-за отсутствующего или повреждённого кэша (§29).

Состояние приложения и незавершённого импорта принадлежит application layer на C++ и не требует фиктивного пустого `ProjectState`. Новый пользовательский проект создаётся и принимается по правилам §13; открытие `.pc2dproj` является отдельной операцией (§28).

Концептуально:

```text
Project
├── SourceInfo
├── PointCacheInfo
├── DensityMapVersions
│   └── DensityMapVersion
│       ├── Identity / Source / BuildMetadata / PNG
│       └── RoughState (ROI / Geometry / HoleGroups / Exclusions / Edits)
├── ActiveDensityMapVersion
├── ReducedPointCloudState
├── PreciseGeometry
├── ProcessingParameters
└── ResultStates
```

Это архитектурные сущности, а не обязательные названия C++ классов.

Основное состояние проекта не должно быть распределено между окнами и QML-компонентами.

Минимальная основа приложения использует `ProjectState` без зависимости от Qt и единственный `ProjectController`, живущий весь сеанс приложения. Controller владеет текущим состоянием и историей команд; `ProjectViewModel` — тонкий QObject-адаптер без копии параметров проекта. QML получает обязательную типизированную ссылку на этот адаптер, не может создать его самостоятельно и не владеет им. QML engine уничтожается раньше адаптера и controller.

В 04.2 production запускается без проекта. `importAscXyz(ImportRequest)` создаёт
новый сеанс после успешного принятия cache; замена требует явного
`replacementConfirmed` именно для этого запроса. В 04.4A «Новый проект» в GUI
начинает выбор ASC/XYZ; legacy controller `newProject()` возвращает `ImportRequired`.
Пустые domain fixtures доступны только через friend test access, включая dev probe.
Принятие задачи 01 этим не пересматривается.

`ProjectSession` объединяет `ProjectState`, storage reference и `QUndoStack`.
Новая пара state/history готовится заранее, commit меняет единственный unique owner.
История объявлена после state и уничтожается раньше него. `ImportedDataset` в core
хранит CacheId, source summary, count/bounds/Z и пути; массив точек и файловые
QObject guards в нём отсутствуют. Core не зависит от cache writer или Qt.

Runtime identity нового экземпляра выдаётся монотонно в течение жизни controller и не используется как сохраняемый project ID или ID версии Density Map. Ревизия входов увеличивается при фактическом изменении, включая Undo/Redo; восстановление прежнего значения параметра не восстанавливает применимость прежнего operation stamp. Исчерпание счётчика проверяется до изменения состояния и истории. Замена или закрытие проекта сначала очищает историю, затем уничтожает прежнее состояние.

Project владеет набором версий и выбором активной версии. PNG и метаданные построения принадлежат версии, её редактируемое Rough-состояние отделено от других версий. Precise Stage остаётся текущим состоянием проекта, а не автоматически восстанавливаемой частью каждой версии.

SelectedRegion внутри Rough-состояния версии задаёт неразрушающую прямоугольную/лассо ROI поверх исходной density map. Rough-состояние также сохраняет исключённые области, необходимые для соблюдения пользовательских решений при следующих операциях. HoleGroup является логической сущностью обоих этапов, а не только частью rough-отображения.

## 10. Системы координат

Необходимо различать три системы координат.

### 10.1. Model coordinates

Основная физическая система.

```text
1.0 = 1 мм
```

В ней хранятся:

- геометрия;
- отверстия;
- размеры;
- допуски;
- области выборки.

Исходные X/Y в Persistent Point Cache, Reduced Point Cloud и при передаче между I/O, pointcloud и precise-алгоритмами представлены `double` (IEEE 754 binary64). Ограничения численной точности определены в [algorithms.md, §3](algorithms.md#3-общие-численные-правила).

### 10.2. Density-map coordinates

Целочисленные координаты пикселей PNG.

Связаны с model coordinates посредством:

- `cell`;
- origin density map;
- ориентации осей.

### 10.3. View coordinates

Экранная система координат Qt Quick.

Используется только для отображения и interaction.

Zoom и pan изменяют только преобразование:

```text
model/pixel → view
```

и не изменяют физическую геометрию или `cell`.

## 11. Coordinate mapping

В проекте должен существовать единый компонент или единый набор функций для преобразований:

```text
model ↔ density pixel
model ↔ view

```

Разные подсистемы не должны независимо реализовывать собственные варианты этих преобразований.

Необходимо однозначно определить:

- положение origin;
- направление оси Y PNG;
- правила округления при переходе в raster coordinates;
- связь с `cell`.

## 12. Persistent Point Cache

После импорта исходный текстовый ASC/XYZ заменяется в обычной работе постоянным локальным бинарным кэшем.

Кэш должен:

- сохраняться между запусками;
- не требовать повторного parsing ASCII;
- позволять работать без доступного исходного файла;
- поддерживать выборочное чтение;
- быть рассчитан на большие объёмы;
- иметь версию формата.

Координаты X/Y записываются в binary64 без дополнительного округления или снижения точности. После повторного открытия reader должен побитово идентично восстановить каждое сохранённое конечное значение `double`, включая знак нуля. Пространственная сортировка, индексация и изменение физического порядка записей не меняют координаты соответствующих исходных измерений.

Исходный point cache логически является immutable dataset.

Ручные операции пользователя не должны изменять его.

Зафиксированный внутренний binary layout v1 и файловый протокол описаны в
[point-cache-format.md](point-cache-format.md). В реализации 5/5 задачи 03 готовы
codec, файловый фундамент, streaming ingest/external sort, CacheWriter,
packed BBox hierarchy и PendingCache с автономным Accept/Discard владением,
CacheReader со spatial queries и строгой полной validation. Reader владеет только
read-only handle; время жизни immutable dataset обеспечивает внешний владелец.
Полная validation дополнительно проверяет канонический порядок Morton128/RecordId
с O(1) состояния. Большой round-trip, ресурсные profiles, HDD queries и crash
lifecycle проверены: [cache-performance-report.md](reports/task-03/cache-performance-report.md).
Application dataset lifecycle реализован в 04.2 по §§9, 13, 25; Save/Open остаётся
задаче 05. Все пять частей
задачи 03 завершены; задача принята пользователем (**ACCEPTED**) после независимого
ревью (**PASS WITH COMMENTS**). Итог — в [плане реализации](implementation-plan.md#03-persistent-point-cache-и-пространственный-доступ).

## 13. Импорт

Импорт выполняется потоково.

При запуске без открытого проекта приложение предлагает выбрать ASC/XYZ. Команда «Новый проект» начинает выбор файла и импорт; если проект уже открыт, пользователь подтверждает намерение заменить его. До успешного завершения импорта текущий проект и его история сохраняются. Отказ от подтверждения, ошибка или отмена не создают новый проект и не уничтожают текущий.

Основная схема:

```text
ASC / XYZ
    ↓
stream parser
    ↓
validation
    ↓
binary cache writer
```

Во время импорта допускается одновременно получать metadata:

- bounding box;
- число точек;
- информацию о Z;
- другие необходимые базовые сведения.

Импорт не должен требовать хранения всех точек в RAM.

Только после успешного импорта application layer атомарно принимает новый проект и его постоянный cache через publication gate (§25), заменяя прежний проект при его наличии. Новый проект получает собственную runtime identity, пустую историю Undo/Redo и выбранный `cell = 1 мм`; значение предыдущего проекта не переносится. Замена не отменяется обычным Undo (§27) и сама по себе не удаляет ранее принятые постоянные файлы кэша.

До принятия нового проекта cache остаётся под cleanup-владением результата импорта; файловая публикация writer не равна принятию проекта. При failure/cancel/discard освобождаются временные ресурсы и непринятый cache по действующему протоколу §12 и [point-cache-format.md](point-cache-format.md).

`cell` не является входом импорта или свойством облака. После принятия проекта он доступен для ручного изменения в ProcessingParameters. Импорт не строит Density Map; её явное построение с выбранным `cell` относится к §15. Save/Open `.pc2dproj` и восстановление при проблемах с кэшем относятся к §§28–31, а не к созданию проекта через импорт.

**Реализованная часть 04.1:** `cadcontour_io` (без GUI/application dependency)
содержит streaming parser и синхронный headless `io::importAscXyz(sourcePath,
finalCachePath, temporaryParent, ResourceLimits, zHandler, cancel, context)`.
Parser принимает borrowed non-sequential binary `QIODevice` в начальной позиции
(обычный QFile/QBuffer) и bounded sink, не создаёт Writer. Sequential devices
отклоняются до чтения: их `atEnd()` не подтверждает окончательный конец потока.
Importer владеет `QFile`, связывает parser с `CacheWriter::create/append/finish`
и возвращает `Result<ImportProduct>`: move-only `PendingCache` и `SourceSummary`
(bytes/physical lines/measurements/первый ненулевой Z). Общие `Measurement`,
`Result/Error` переиспользуются из cache; source errors дополняются ограниченным
`SourceLocation` (строка, byte column, координата, fragment). Binary format v1 не меняется.

Суммарный budget импортера включает фиксированный parser/source reserve,
учёт source path и один source handle; остаток передаётся Writer по существующему
протоколу. Источник читается unbuffered последовательными блоками. До/после чтений,
между bounded parsing intervals/batches и перед/после finish проверяется cooperative
cancel; Writer/Sorter получают тот же callback. QFile закрывается до finish.
При успехе `PendingCache` остаётся cleanup owner в том же потоке; `releaseToOwner()`
не вызывается. Failure/cancel уничтожает только собственные временные данные.

QFile поддерживает Unicode/UNC paths; importer сверяет начальные и конечные size/mtime
и число прочитанных байтов. Это обнаружение доступных признаков изменения/усечения,
а не гарантия неизменности файла: in-place rewrite с сохранением size/mtime может
не обнаружиться. Блокирующий OS read не прерывается cancellation callback.
Z-handler самого importer остаётся синхронным. В 04.3 application worker связывает
его с `WorkerControl::confirmNonZeroZ`: один bounded request `{OperationId, UUID,
physical line, Z}` передаётся через OperationContext и `poll()` в поток controller.
`ProjectController::pendingNonZeroZ()` возвращает optional ожидающего запроса,
`nonZeroZConfirmationChanged` уведомляет consumer, `answerNonZeroZ` принимает
Continue/Cancel. UUID отделяет запросы даже при пересоздании controller и повторении
OperationId. Недействительный/повторный ответ отклоняется как Rejected/InvalidValue;
wrong-thread, reentrant и shutdown команды сохраняют обычные command errors.

Consumer явно регистрируется через `setNonZeroZConsumer(QObject*)` до запуска,
в том же Qt-потоке; регистрация означает готовность обслуживать запросы. Его
отключение или уничтожение отменяет активный импорт. Worker не хранит QObject
и не вызывает GUI callbacks. Без consumer используется пустой parser handler:
плоский файл импортируется, ненулевой Z даёт InvalidInput с диагностикой требования
decision handler, без ожидания или автоматического Continue. Это
fail-closed политика для callers без consumer; timeout не используется.

На Z-wait чтение и передача measurements остановлены, bounded parser buffers
остаются в worker. Continue продолжает тот же проход; Cancel возвращает Cancelled,
сохраняя прежний проект и history. Close отменяет также первый импорт из NoProject.
Публикация после Continue по-прежнему требует отдельного Ready/Accept (§25).
В 04.4A production `ProjectViewModel` регистрируется единственным GUI consumer
до импорта. QML вызывает стартовый выбор через `Qt.callLater` после Component completion,
однократно за сеанс адаптера; отложенный метод привязан к времени жизни окна.
Cancel оставляет NoProject. Нативный `QtQuick.Dialogs.FileDialog`
передаёт QUrl; C++ проверяет local-file semantics, absolute Windows/UNC path,
расширение и отсутствие query/fragment/credentials/NUL, затем использует `toLocalFile()`.
Проверка доступности source и весь файловый I/O остаются в worker.

Выбор и подтверждение замены имеют одноразовый UI token. До FileDialog controller
выдаёт `ImportContext` (optional project stamp, application epoch и номер последней
операции). GUI передаёт его как `ImportRequest::expectedContext`; controller
повторно сверяет контекст и доступность запуска. Изменение контекста, Busy или Closing
снимают выбор; старый callback не разрешает новый импорт. После синхронного UI-уведомления
adapter повторно проверяет именно созданный token, контекст и Open перед запросом
FileDialog; QML также не открывает диалог для отозванного выбора. Это дополнительная проверка
перед запуском, прежний publication gate остаётся обязательным.

Z-диалог хранит UUID отображаемого запроса, а adapter сверяет его с актуальным
`pendingNonZeroZ()` и передаёт существующий typed request в `answerNonZeroZ`.
Пользовательское закрытие означает Cancel. Программное закрытие предварительно
снимает UI token, исключая ложный ответ. Destructor ViewModel отключает входящие
controller signals до QObject destruction: отзыв consumer может синхронно отменить
worker, но уже не вызывает методы уничтоженного derived adapter. Синхронный внешний
обработчик уведомления или команды может уничтожить adapter; продолжения после
таких вызовов проверяют время жизни и не обращаются к уничтоженному QObject.

Карточка читает только принятый `ProjectState::dataset()`. Count и диагностические
64-bit counters передаются строками, coordinates/Z — shortest round-trip binary64
без группировки, с технической десятичной точкой. Ошибки импорта и ввода cell
разделены; progress/failure не меняют draft/selection/error cell.

GUI выбирает `interactiveResources`, worker разрешает его в обычный ненулевой
ResourceLimits на томе storage: рабочий бюджет 128 MiB, 32 файла, дисковый бюджет
доступного места после резерва 64 MiB и 5% оставшегося объёма. Это политика одного
импорта, а не предел RAM приложения или ограничение размера исходного файла.
Explicit limits headless callers сохраняются. Неизвестный/недостаточный disk budget
даёт ResourceExhausted; snapshot свободного места не гарантирует последующую запись.

Необязательный синхронный observer импортера сообщает только границы Parsing и
BuildingCache; application добавляет Preparing/Finalizing, Z-wait и terminal outcome.
Сортировка, индекс и sealing объединены в BuildingCache. Total неизвестен, GUI
использует indeterminate без вымышленных процентов. Mailbox и threading не менялись.
Большие сквозные прогоны остаются в 04.4B. Подробности — [04.4A](reports/task-04/asc-xyz-gui-check.md),
[04.1](reports/task-04/asc-xyz-import-check.md),
[04.2](reports/task-04/asc-xyz-application-check.md), [04.3](reports/task-04/nonzero-z-confirmation-check.md).

## 14. Пространственный доступ к cache

Архитектура persistent cache должна позволять читать только точки, относящиеся к требуемой пространственной области.

Для этого предусматривается spatial index или эквивалентная организация данных.

Для v1 выбран Morton128 ordering → packed point pages → BBox hierarchy с bounded
external sort при построении и одним packed DFS при запросах. Сравнение с
source-order pages и тем же BBox index, в том числе на HDD, подтвердило полезную
выборочность с измеренной ценой построения. Layout/каноничность определены в
[point-cache-format.md](point-cache-format.md), измерения и ограничения — в
[cache-performance-report.md](reports/task-03/cache-performance-report.md). Это не утверждение
универсального выигрыша для каждого распределения или полного scanAll.

Приоритетом является последовательный и локализованный I/O, подходящий для HDD и медленных файловых систем.

## 15. Density Map

Density map является самостоятельным dataset внутри версии проекта. Пользовательский контракт хранения и переключения — [requirements.md, §8](requirements.md#8-фиксированный-размер-cell).

Версия должна иметь как минимум:

```text
version identity
PNG
cell
origin
width
height
build parameters
source data / cache identity and reference
associated Rough State
```

Один пиксель всегда соответствует:

```text
cell × cell мм
```

Zoom не изменяет density map.

Параметры будущего построения отделены от метаданных уже построенной версии. Выбранный `cell` хранится в ProcessingParameters проекта, при создании через импорт равен 1 мм и задаётся пользователем вручную; каждая построенная версия сохраняет собственное использованное значение. Изменение выбранного `cell` не меняет PNG или метаданные существующей версии; создание новой карты запускается явно. PNG и метаданные построения не изменяются при редактировании Rough Stage. Автоматическая рекомендация `cell` не является утверждённой функцией или зависимостью построения карты — [requirements.md, §7](requirements.md#7-построение-карты-плотности).

Идентичность версии не сводится к `cell` или ревизии текущего проекта. Для совместимости существенны исходные данные и параметры построения (§23). Повторное построение публикует новую версию либо явно подтверждённую замену по requirements.md, §8; конкретная политика остаётся открытой.

Переключение выбирает существующие PNG и Rough-состояние без пересчёта и переноса правок между версиями. Application layer соблюдает reset (§6.2) до изменения активного Rough Stage; версия не является архивом Precise Stage.

Первый этап использует конкретную построенную PNG как источник raster data.

Автоматический multi-resolution/LOD, изменяющий физическое raster resolution при zoom, не используется.

## 16. Rough Geometry

Rough geometry отделена от precise geometry.

Она содержит внешний контур, активные отверстия, связи с HoleGroup, внутренние вырезы и сведения об исключённых областях. Удалённые или отфильтрованные по размерам отверстия не становятся автоматически cutouts и не участвуют в reduced-cloud extraction.

Полный повторный Find Rough Holes заменяет набор и связанные ручные правки; прежнее удаление не препятствует новому обнаружению. Текущий диапазон размеров по-прежнему применяется. Представление исключений является деталью реализации.

Внешний rough-контур может храниться как замкнутая полилиния.

Внутренние rough-контуры также могут использовать представление, подходящее для простого ручного редактирования.

Rough geometry должна храниться в model coordinates, даже если получена из PNG. Анализ и ручные изменения относятся к версии карты (§15); смена `cell` не является масштабированием этой геометрии.

## 17. Повторные rough-операции

Каноническое пользовательское поведение определено в [requirements.md, §§12–18](requirements.md#18-взаимодействие-операций-первого-этапа): повторная операция полностью заменяет результат без автоматического сопоставления со старыми объектами; другая операция использует текущие rough-данные и исключения.

Перед заменой ручных изменений требуется предупреждение. Успешная замена является одним логическим Undo-действием внутри rough-stage. Повторный поиск holes может заново обнаружить удалённые отверстия, но обычные последующие операции этого не делают.

Если операция меняет rough-входы после начала precise-stage, до изменения требуется подтверждённый межэтапный сброс без Undo (§6.2).

## 18. Reduced Point Cloud

Reduced point cloud является отдельным рабочим dataset.

```text
Persistent Point Cache
        │
        ▼
spatial filtering around rough geometry
        │
        ▼
Reduced Point Cloud
```

Point cache остаётся неизменным.

Reduced cloud может редактироваться пользователем.

Передача выбранных исходных X/Y из cache в рабочий dataset и далее в Precise Stage сохраняет их binary64-представление (§10.1), независимо от способа хранения reduced cloud. Вычисление расстояний для фильтрации не заменяет координаты измерений вычисленными значениями; пользовательский контракт — [requirements.md, §21](requirements.md#21-переходы-между-этапами).

Удаление шумовой точки означает изменение рабочего reduced cloud, а не исходного persistent cache.

Архитектура позволяет явно полностью перестроить reduced cloud из cache: создаётся новый рабочий набор, старые удаления не обязаны переноситься.

Сохранение и повторное открытие проекта сохраняют ручные удаления. Способ хранения рабочего cloud и его правок остаётся открытым (§45, Reduced Cloud Storage).

Выборка использует максимальное расстояние от текущей активной rough-геометрии в миллиметрах; исключённые rough-области не используются для выборки. Изменение rough-входов сбрасывает второй этап по §6.2.

## 19. Precise Geometry

Precise geometry хранит замкнутые контуры из итоговых CAD-примитивов первой версии.

Исчерпывающий набор (domain type → геометрический тип):

```text
LineSegment → LINE
CircularArc → ARC
Circle      → CIRCLE
```

Контур — замкнутая упорядоченная последовательность LineSegment/CircularArc либо самостоятельный Circle. Этот контракт распространяется на автоматическое построение, ручное редактирование, precise-stage, Geometry Optimization, topology, validation и export. SPLINE/BSpline и ELLIPSE не поддерживаются; расширение модели требует отдельного изменения требований.

Precise geometry является независимой от Qt Quick.

Renderer получает её для отображения, exporter — для записи DXF, algorithms — для анализа и модификации.

Связи отверстий с HoleGroup сохраняются при переходе между этапами. Rough group size используется для начального описания и выборки; precise geometry хранит индивидуальные измеренные центры и размеры. Общий одинаковый precise-диаметр группы не требуется.

## 20. Топология контуров

Финальный контур нельзя рассматривать как произвольный несвязанный список кривых.

Для последовательности LINE/ARC модель должна хранить:

- порядок элементов;
- связи соседних элементов;
- общие endpoints;
- замкнутость;
- тип соединения.

Минимальные смысловые типы соединения:

```text
Corner
Tangent
```

Для любого соединения обязательна позиционная непрерывность.

Для `Tangent` дополнительно требуется совпадение направления касательных.

`Corner` не должен автоматически превращаться в плавное соединение.

Непрерывность является свойством domain geometry, а не только её визуального отображения. Самостоятельный CIRCLE замкнут аналитически и не имеет junctions с другими primitives своего контура. Внешний и все внутренние контуры всегда замкнуты. Rough polyline (§16) не является итоговым примитивом или DXF POLYLINE/LWPOLYLINE.

Модель первой версии соответствует [requirements.md, §27](requirements.md#27-непрерывность-контуров): один внешний контур и внутренние holes/cutouts без запрещённых пересечений, касаний независимых границ и вложенных material islands. Касающиеся области могут описываться единой корректной формой, но не двумя независимыми границами. Общие endpoints соседних primitives одного контура допустимы и обязательны для C0.

## 21. Automatic и Fixed Geometry

На precise stage необходимо различать как минимум:

```text
Automatic
Fixed
```

`Fixed` означает объект, явно зафиксированный пользователем после создания или ручного изменения.

Автоматическая операция:

- не изменяет fixed geometry;
- рассматривает её как constraint;
- строит оставшиеся свободные элементы относительно неё.

Например fixed-линия задаёт:

- положение;
- направление;
- endpoints;
- требуемый характер соединений,

которые должны учитываться при построении соседних свободных элементов.

Пользователь может снять Fixed: `Automatic → Fixed → Automatic`. Снятие фиксации не запускает автоматический fitting. Fixed относится к precise geometry и не означает подтверждение rough-state.

## 22. Односторонний допуск

Требование сохранения материала является обязательным контрактом precise processing.

Архитектурный pipeline должен содержать проверку результата:

```text
Precise fitting
      ↓
Geometry validation
      ↓
accepted geometry
      или
failure
```

Автоматическая геометрия не может считаться успешно построенной, если она нарушает требуемое направление допуска.

Для внешнего контура допустимое автоматическое отклонение направлено наружу.

Для отверстий и внутренних вырезов допустимое автоматическое отклонение не должно увеличивать удаляемую область за счёт материала.

Конкретный математический способ проверки определяется в `algorithms.md`.

## 23. Результаты вычислений и их актуальность

Следует различать наличие/актуальность построенного dataset и состояние выполняемой операции. Логически результат может быть Missing, Current или Outdated; операция — Running, successful, cancelled или failed. Это не обязательные enum или классы.

Неудачная попытка пересчёта не заменяет предыдущий корректный результат. Внутри одного этапа изменение relevant inputs может сделать зависимый результат Outdated, но не запускает тяжёлое вычисление автоматически.

В precise-stage UI сообщает о «неприменённых изменениях». При DXF export application layer предупреждает, что geometry ещё не перестроена по текущим входам; пользователь отменяет экспорт или явно продолжает экспорт текущей построенной geometry. Exporter сам не выполняет fitting.

Совместимость сохранённой версии Density Map проверяется по её исходным данным и существенным параметрам построения. Изменение выбранных параметров будущего построения или активной версии не делает остальные версии неактуальными само по себе.

Ревизии текущего состояния для защиты фоновых операций (§25) и совместимость ранее построенных результатов имеют разный смысл. Совпадение или различие ревизий само по себе не разрешает и не запрещает повторное использование версии. Идентичность версии, provenance и применимость worker не должны подменять друг друга.

Цепочка PointCache → DensityMap → RoughGeometry → ReducedPointCloud → PreciseGeometry описывает зависимости данных, а не единое правило Outdated для всех переходов.

При изменении rough-входов после начала precise-stage действует полный подтверждённый сброс без Undo (§6.2). Старый второй этап не сохраняется в текущем проекте как Outdated. Outdated допускается внутри этапа там, где нужен для зависимых результатов.

## 24. Длительные операции

Любая потенциально трудоёмкая операция запускается через application layer только после явного действия пользователя.

Длительная операция должна поддерживать:

```text
start
progress
cancel
success
failure
```

GUI должен оставаться отзывчивым.

Application layer допускает только один физически выполняющийся worker. Повторный запуск до подтверждённого завершения возвращает Busy; очереди и автоматического повторного запуска нет. Запуск принятой операции получает неповторяемый `OperationId`, отдельный от `OperationStamp` проекта/входов; переполнение отклоняется до изменения состояния.

Progress передаётся через ограниченный mailbox последнего значения: фаза, выполненное количество и необязательный total. GUI читает его периодически; неизвестная продолжительность не превращается в фиктивный процент. Состояние операции и уведомления о нём отделены от project state и Undo. Они не сбрасывают draft, ошибку ввода, курсор или выделение поля параметра; поле синхронизируется при изменении соответствующего параметра/проекта либо явном Apply с канонизацией no-op.

Cancellation кооперативна и не использует принудительное завершение потока. Запрос отмены немедленно и необратимо отзывает право публикации; проверка worker на checkpoint определяет лишь скорость остановки. Изменение relevant inputs, смена/закрытие проекта и reset также отзывают это право. No-op и отклонённая команда не инвалидируют входы. Worker success, cancellation, failure и application discard различаются; commit и полное завершение потока — разные события.

Для явного Save действует контракт §28.1: cell/Undo/Redo не инвалидируют захваченный
snapshot. До permission Cancel/Close/Shutdown отзывают право commit; после permission
файловый результат обязательно дожидаются, Cancel возвращает NoChange, Close/замена — Busy.

Z-confirmation — отдельное ожидание до Ready, не PublicationDecision. Request,
ответ и cancellation flag изменяются под одним mutex с predicate condition variable.
Worker просыпается при решении, cancellation, Discard или отзыве запроса;
cancel/invalidation/shutdown выставляют cancellation и снимают request под этим
mutex, затем notify. Atomic flag остаётся доступен обычным checkpoints. Поэтому
отмена до входа в wait не теряет пробуждение. Ответ потребляет identity один раз;
Continue не отменяет общий cancellation и не даёт права публикации. Операция
остаётся Busy до прежнего native completion/join. Observers и test hooks вызываются
вне mutex; уведомление, обнаруженное внутри controller command, откладывается
до возврата команды. Нормальный consumer может синхронно ответить на уведомление.
Destructor отменяет оба ожидания и drain без GUI event delivery (§26).

К длительным операциям относятся как минимум:

- импорт;
- создание density map;
- автоматический rough-анализ;
- создание reduced cloud;
- precise fitting;
- geometry optimization.

## 25. Атомарность вычислительных операций

Worker не должен постепенно изменять основной `ProjectState` во время вычисления.

Схема публикации через единственный production gate application layer:

```text
Operation inputs / immutable snapshot
        ↓
background computation
        ↓
temporary result
        ↓
Ready: structured outcome / temporary product
        ↓
initial applicability check
        ↓
prepare typed candidate + fallible finalize / validation
        ↓
final applicability check
        ↓
noexcept atomic commit → Accept
```

При:

- ошибке;
- отмене;
- исключении;

частично вычисленный результат не должен становиться текущим состоянием проекта.

Результат фоновой операции над открытым проектом публикуется только в тот проект и относительно того состояния входных данных, для которого она была запущена. При смене проекта, изменении relevant inputs или межэтапном reset старый worker не должен восстановить сброшенные данные или перезаписать более новое состояние.

Snapshot включает идентичность целевой версии и применимое состояние её Rough-входов, когда операция относится к Rough Stage. Переключение версии не позволяет старому worker записать результат в другую версию или заменить более новые правки. Совместимость сохранённой карты (§23) не является разрешением публикации задержанного результата.

Snapshot сам по себе не обеспечивает этот инвариант. Для операции над открытым проектом gate сверяет OperationId, исходный ProjectIdentity/InputRevision, отсутствие отзыва публикации и открытое состояние приложения непосредственно перед commit. При появлении версий/Rough-входов их идентичность и ревизия включаются в тот же контракт; это не критерий совместимости сохранённых версий.

Импорт для создания или замены проекта (§13) использует тот же контракт атомарного принятия, но не требует заранее открытого проекта или фиктивного ProjectIdentity. Gate проверяет OperationId, применимость именно этого запроса создания/замены к исходному контексту приложения, отсутствие отзыва публикации и открытое состояние приложения. Задержанный результат не может заменить проект, открытый или созданный после запуска импорта. Подготовка нового состояния и передачи владения cache не меняет текущий проект и его историю; только успешный commit принимает новый проект.

В 04.2 snapshot содержит optional исходный stamp (NoProject без фиктивной identity),
application context epoch, вид операции и факт разрешения замены. Gate сверяет их
вместе с OperationId/cancel/revocation/Open; epoch и необратимый отзыв исключают
NoProject ABA. Import adapter сохраняет Ready/Accept/Discard и native join.

Fallible preparation не изменяет текущий результат, предыдущий корректный результат и историю. После final check commit не выполняет allocations, dialogs, обработку событий или throwing history pushes; согласованные владельцы меняются атомарно не более одного раза. Будущий adapter реальной операции должен подготовить также её dataset/history изменения и проверить их атомарность; проверочный product задачи 02 не доказывает корректность cache/PNG publication adapters и не становится domain dataset.

Worker после Ready ожидает единственное решение Accept/Discard по predicate condition variable. Все ветви gate дают решение. Borrowed product удерживается lease до конца preparation, в том числе при reentrant shutdown; worker освобождает discarded product и временные ресурсы вне mutex. Для verification Accept передаёт product application layer. Shutdown заранее выставляет Discard, если решения ещё нет, и уведомляет worker до любого ожидания; уже выполненный Accept не отменяется.

Для import через Ready передаётся только `ImportReadyProduct`: metadata и пути.
Worker-only `WorkerOutcome` содержит `WorkerImportProduct`, но OperationContext
хранит отдельный `ReadyOutcome`, структурно не содержащий PendingCache/QTemporaryDir.
PendingCache остаётся локальным в execute до окончательного решения; исключительные
пути и уничтожение QTemporaryFile выполняются в worker.

Import candidate заранее получает domain metadata и storage retention reference.
После final applicability check borrowed lease под mutex повторно проверяет
Pending/cancellation, выполняет noexcept обмен сеансов и фиксирует Accept без
callbacks между ними. Только затем уведомляются observers. Worker ожидает также
освобождения lease, затем при Accept вызывает directory.setAutoRemove(false) и
PendingCache.releaseToOwner() в своём потоке. Решение уже необратимо: Close/Shutdown
и уничтожение сеанса не удаляют принятые файлы даже до этой финализации. При Discard
guards удаляют cache и каталог. Busy/terminal/shutdown Ready по-прежнему требуют
native completion и Qt join.

Это правило особенно важно для длительных операций на HDD или сетевых данных.

## 26. Потоки

GUI работает в основном Qt GUI thread.

Длительные вычисления выполняются вне GUI thread.

Background worker не должен произвольно изменять QML objects или общий mutable project state.

Связь между GUI и worker должна передавать:

- immutable input или snapshot;
- progress;
- cancellation request;
- завершённый result;
- structured error.

Текущая реализация использует `QThread::create()` и один worker. Worker первым действием подтверждает вход в wrapper; `start()` без возвращаемого результата, отсутствие signals и истечение тайм-аута не являются доказательством launch failure. Неподтверждённый запуск остаётся Starting/Busy до подтверждённого входа либо join завершённого потока без входа.

На Windows освобождение execution context и QThread, terminal notification и новый запуск требуют одновременно полного завершения системного потока и успешного Qt join. Независимый real thread HANDLE получается через DuplicateHandle в worker и закрывается RAII-владельцем. Только `WAIT_OBJECT_0` от WaitForSingleObject подтверждает завершение; TIMEOUT/FAILED удерживают ресурсы. При отказе DuplicateHandle вычисление не начинается и возвращается structured failure с системным кодом. Worker не выходит из handshake без независимого handle; application layer может получить его через OpenThread для этого ещё живого потока. Отказ получения/ожидания удерживает Busy и диагностируется; аварийный destructor также не освобождает неподтверждённые ресурсы и может ждать, пока системное наблюдение недоступно. Это не повторный запуск операции.

Guard добавлен после воспроизведённого расхождения установленного Qt 6.12.0 с обещанием `wait()` на Windows: `wait(0)` возвращает true при заблокированном C++ TLS destructor. Основание и отдельные Debug/Release reproducer/regression tests — [thread-completion-check.md](reports/task-02/thread-completion-check.md).

Штатное закрытие проходит Open → Closing → Ready. Кнопка закрытия, системное закрытие окна и application Quit используют одну процедуру: запрет новых команд, отзыв публикации, cooperative cancel, Discard + notify. GUI продолжает обрабатывать события до native completion/join, затем закрывает окно и завершает event loop. Повторное закрытие идемпотентно. Destructor fallback выполняет тот же Discard/notify и join до уничтожения project/history/adapter/context, без `processEvents()` и без зависимости от queued callbacks; неожиданный выход из event loop может блокировать destructor до безопасного завершения.

Terminal completion согласует operation state и shutdown readiness до внешних уведомлений. Синхронные observers не могут нарушить незавершённый terminal transition: повторный запуск во время terminal notification отклоняется как `ReentrantCommand`. После полного завершения transition новый запуск допускается, если приложение остаётся Open; completion старой операции не меняет состояние нового запуска. Shutdown Ready требует подтверждённого физического завершения и освобождения worker.

## 27. Undo/Redo

Ручные изменения project/domain state должны поддерживать Undo/Redo.

К ним относятся:

- добавление геометрии;
- удаление;
- перемещение;
- изменение параметров;
- изменение отверстий;
- редактирование контуров;
- удаление точек;
- фиксация/разрешение автоматического изменения;
- замена существующего результата повторной автоматической операцией.

Допускается использование Qt Undo Framework.

Undo-команда должна изменять domain/project state, а не только визуальное состояние QML.

Application-команда сначала проверяет входы и возможность изменения, затем синхронно завершает изменение состояния и истории. Внешнее уведомление публикуется только после этого: наблюдатель видит согласованные параметры и доступность Undo/Redo. Повторный вход через обработчики этого уведомления отклоняется. Отклонённая команда и no-op сохраняют историю, включая redo-ветку.

Обычный Undo/Redo действует внутри rough-stage и precise-stage. Полный межэтапный сброс не поддерживает Undo; история не должна возвращать сброшенный второй этап или обходить reset при изменении rough-входов. Второй экземпляр reduced cloud и precise-данных ради отмены такого сброса не требуется.

История Undo/Redo принадлежит текущему проекту и сеансу и после повторного открытия проекта не восстанавливается. При успешном создании или замене проекта через импорт прежняя история очищается до уничтожения прежнего состояния и в новый проект не переносится; обычный Undo не возвращает предыдущий проект. До успешного принятия импорта история текущего проекта сохраняется (§13). Сохранённые версии и их правки не зависят от истории команд.

Команды rough-stage адресуют соответствующую версию и изменения domain state. История не хранит полные копии PNG или других тяжёлых datasets; следует предусмотреть ссылки на существующие версии. Время жизни datasets учитывает project state, save/recovery и выполняемые операции, а не только Undo. Очистка истории не удаляет версии. Переключение через Undo/Redo также соблюдает межэтапный reset (§6.2).

## 28. Project Persistence

Рабочий файл проекта имеет расширение:

```text
.pc2dproj
```

Архитектурно `.pc2dproj` является manifest/state-файлом, а не обязательным многогигабайтным контейнером всех данных.

Пример структуры project-owned data:

```text
ProjectName/
├── ProjectName.pc2dproj
└── data/<storageId>/datasets/<CacheId>.pc2dcache
```

Для реализованной 05.1 этот layout и точная UTF-8 JSON schema v1 определены в
[project-manifest-format.md](project-manifest-format.md). Будущие dataset kinds
расширяют версионированную схему без изменения базового механизма paths/retention.

Промежуточный storage 04.2: `AppLocalDataLocation/projects/project-<storage UUID>-<unique>/`
с `datasets/<attempt UUID>.pc2dcache` и отдельным временным `scratch-*`.
Root можно переопределить в C++ для изолированных tests. Каталог попытки создаётся
эксклюзивно, Writer не перезаписывает существующие файлы. CacheId из metadata,
storage UUID, OperationId и runtime identity независимы. В 05.1 единственный physical
binding domain dataset — `shared_ptr<const DatasetLocation>` со storage identity,
directory и относительным dataset path; ProjectSession больше не дублирует пути.
Этот retention reference можно удерживать в snapshots workers/Undo. Уничтожение
последней ссылки не удаляет принятые файлы: Close, замена и очистка history безопасны,
допускается накопление caches. До Accept cleanup по-прежнему принадлежит worker
PendingCache/QTemporaryDir; irreversible gate и worker finalization не изменены.
Save/Save As реализованы в 05.2 (§28.1), Open — в 05.3 (§28.2);
Recovery реализован в 05.4 (§31); автоматической GC нет. При аварии процесса могут остаться непринятые attempt/scratch
files; автоматического scavenger нет.

`ProjectState` остаётся Qt-независимой domain model без I/O. Его постоянный `ProjectId`
(UUID bytes в RFC order) создаётся при подготовке import candidate до noexcept commit
и публикуется только при Accept. Он не меняется от cell/Undo/Redo; ошибка или отмена
не заменяет identity открытого проекта. Runtime identity/input revision остаются
отдельными applicability tokens и не сериализуются.

`cadcontour_persistence` (core/cache metadata + Qt Core) содержит отдельные
ProjectSnapshot, JSON codec и path validation. Snapshot включает project/storage/snapshot
identities, mm, выбранный cell, справочные source metadata, descriptor Point Cache v1
и ссылку state на CacheId. Storage/snapshot IDs задаются вызывающим кодом; metadata
projection не создаёт published save baseline. Uint64 и binary64 хранятся строками
с точным round-trip, включая signed zero. Обязательные поля, типы, ranges, metadata,
references и неизвестное содержимое проверяются строго. Несовместимое расширение
требует новой версии, миграционная система не добавлена.

Codec не открывает datasets, не вызывает CacheReader, validate/scanAll, не копирует
cache и не запускает вычисления. Отсутствие/недоступность/повреждение dataset отделено
от корректности manifest. Явные caller-selected bytes/tokens/depth budgets проверяются
до DOM; bounded device reader проверяет размер до чтения. Это admission policy metadata,
не фиксированный лимит количества будущих версий и не обещание peak RSS.

Save 05.2 сначала подготавливает полностью завершённые immutable файлы без overwrite,
затем публикует manifest. Новый DatasetLocation подготовлен до permission, current
reference заменяется после подтверждённого успеха; старые holders удерживают прежний binding.

Канонический перечень восстанавливаемого состояния определён в [requirements.md, §32](requirements.md#32-сохранение-проекта). Он включает выбранные параметры будущего построения (в том числе `cell`), все версии Density Map с их собственными параметрами и Rough-состояниями и активную версию, HoleGroup обоих этапов и ручные удаления точек reduced cloud независимо от способа хранения. При открытии восстанавливается сохранённый выбранный `cell`; начальное 1 мм относится к новому проекту через импорт. Связи версии с PNG, metadata, source cache и Rough-состоянием восстанавливаются согласованно; история Undo не сериализуется. Детальные layout и схемы определяются при реализации. Различаются версия persistent format (§30) и идентичность результата (§15).

Опубликованный project save ссылается только на полностью записанные согласованные project-owned datasets. Неудачная запись сохраняет предыдущее корректное сохранение. Реализованный протокол записи описан в §28.1.

### 28.1. Явные Save / Save As (05.2)

C++ API controller: `saveProject(SaveRequest)` и `saveProjectAs(SaveRequest)`.
Первый Save требует абсолютного `.pc2dproj` path; повторный Save может использовать
известный path без аргумента. Save As в тот же canonical directory с эквивалентным
именем выполняет metadata-only Save. Другое имя в том же directory — Conflict:
автоматическое переименование и второй manifest одного storage не поддерживаются.
Новый каталог получает новый storageId; ProjectId/CacheId сохраняются, каждый
опубликованный snapshotId новый. Uncertain commit запрещает следующий Save в этом
сеансе до проверки через последующее Open.

Протокол отличается от вычислительных операций §25:

```text
owner: capture metadata + retain dataset binding
worker: directory lock + source lease → bounded copy (если требуется)
        → completed immutable dataset → staged manifest + prepared binding/baseline
owner: Ready lease → session applicability → irrevocable publication permission
worker: final filesystem/conflict checks → atomic manifest commit → fixed-size receipt
        → release file resources → native completion / Qt join
owner: persisted receipt → noexcept binding/baseline exchange → terminal notification
```

Import сохраняет прежний Accept с немедленным noexcept обменом state/history.
Для Save Accept означает только permission: он не меняет baseline и не объявляет
Succeeded. Commit исполняется в worker без controller/context mutex. До permission
действует cancellation; после него shutdown ждёт исход и native join. Destructor
drain не требует доставки receipt; опубликованный manifest остаётся источником
истины для будущего Open, даже если приложение не обработало receipt.

Save applicability проверяет OperationId, runtime session identity/context epoch,
Open и отсутствие отмены, но не input revision. Более поздние cell/Undo/Redo остаются
в текущем ProjectState. Receipt меняет только физический binding и saved baseline;
он не заменяет текущее содержимое snapshot, не очищает историю и не вызывает setClean.
Dirty сравнивает ProjectId, cell, source metadata, CacheId, count/bounds/Z с фактически
сохранённым содержимым. Runtime revisions, paths физической копии, storage/snapshot
IDs и history сами по себе не являются dirty. Импортированный проект без baseline dirty.

`cadcontour_persistence` владеет файловой транзакцией; application слой — запуском,
gate, session binding и baseline. Ready содержит shared immutable metadata;
QSaveFile/QTemporaryFile, QLockFile и handles остаются в worker. Необходимые application allocations
завершаются до permission. Save errors содержат code, phase, native system code и
bounded diagnostic; файловые ошибки не показывают dialogs.

Блокировка `.pc2d-save.lock` кооперативна и действует на весь canonical directory.
Новый target не заменяет существующий файл и отклоняет другие `.pc2dproj`/готовый
`data`. При повторном Save непосредственно перед commit под тем же lock сверяются
ожидаемые ProjectId/storageId/snapshotId и SHA-256 manifest. Повторяются path/reparse
checks; directory handles запрещают rename/delete удерживаемых каталогов, dataset
handles запрещают write/delete до конца операции. Это не защита от произвольного
стороннего процесса, writable mapping, hard-link/ancestor alias или аппаратного отказа.

Первый Save/Save As копируют cache блоками 64 KiB, сверяют размер, SHA-256 source/copy,
v1 envelope и page checksums при readback; index/ID validation и пересчёт не выполняются.
Обычный Save проверяет file identity (volume/file ID, size, last-write/change times),
header/footer checksums, completion/layout и metadata. Полного scan/validate нет;
повреждение середины файла без изменения наблюдаемой identity/timestamps этой
проверкой не обнаруживается. Source ASC/XYZ не читается.

Dataset rename не перезаписывает существующий файл. С этого момента dataset
консервативно удерживается даже при отмене/ошибке manifest или потере receipt; GC нет.
Unpublished temporary files принадлежат worker guards. Новый manifest публикуется
same-directory QTemporaryFile::rename без overwrite: даже файл, созданный сторонним
процессом после последней проверки, сохраняется. Обычная замена известного manifest
использует QSaveFile с отключённым direct-write fallback. Неуспешный/бросивший
replacement commit классифицируется Uncertain: baseline
и current binding не меняются, prepared path/IDs/digest доступны через unconfirmedSave,
данные сохраняются для проверки фактического manifest. Ошибка необязательных
post-commit receipt/cleanup hooks оставляет Persisted и отдельный cleanupWarning.
Crash может оставить staging/orphan files; абсолютная power-loss durability не обещается.

Реализация, проверки и ограничения — [отчёт 05.2](reports/task-05/save-implementation.md).

### 28.2. Open и частичная доступность (05.3)

`ProjectController::openProject(OpenRequest)` принимает абсолютный `.pc2dproj` path,
ManifestLimits и бюджет Reader (по умолчанию 4 MiB / 4096 tokens / depth 32 для
manifest, 1 MiB / два handles для cache). Это overridable admission profiles,
не ограничения размера облака или RAM приложения. `replacementConfirmed` обязателен
при любом текущем проекте; optional `expectedContext` использует существующий
ImportContext, захваченный через `importContext()`, и защищает от устаревшего выбора.
Без него headless caller подтверждает именно контекст вызова. GUI относится к 05.5.

Worker читает manifest существующим bounded `readManifest`, получает digest ровно
декодированных bytes без повторного чтения, разрешает пути от фактического canonical
каталога выбранного документа. Неверный manifest даёт structured `openError` и не
заменяет сеанс; source ASC/XYZ не открывается. Dataset path/reparse failure сохраняет
metadata проекта, но не предоставляет cache операциям.

Ограниченная проверка использует `CacheReader::open`: физический размер,
header/footer/version/checksums, packed hierarchy shape и одну корневую index page,
точное совпадение CacheId/count/bounds/Z с descriptor. Read-only lease запрещает
обычные write/delete во время проверки; identity наблюдается по retained handle.
Manifest закрывается до dataset probe; lease + Reader укладываются в два handles.
Для v1 непустого cache читается 73 728 bytes, ноль point pages; нет копирования,
scratch, scanAll, validate, сортировки, PNG или reduced cloud.

`CacheAvailability` принадлежит application session отдельно от domain content и
saved baseline. Различаются AvailableLimited, Missing, Corrupt, Unsupported, FileIO,
UnsafePath; диагностические cache/path errors сохраняются. AvailableLimited означает
только доступность после ограниченной проверки, без полной проверки страниц/RecordId.
Принятый импорт тоже не объявляется полностью проверенным Reader validation.
Resource admission failure не подменяется частичным success: прежний сеанс сохраняется.

Отказ Win32-запроса identity не является доказательством corruption: обычный отказ
даёт FileIO, известный отказ памяти/системных ресурсов — ResourceExhausted без
публикации candidate. GetLastError фиксируется сразу после неуспешного API;
исходный код сохраняется в diagnostic существующего Error. Только две успешно
полученные различающиеся identity считаются изменением файла. Оба наблюдения
resolver сохраняют его категории: FileIO, Missing при `exists=false`, UnsafePath
при обнаруженном нарушении path safety.

Ready переносит только immutable LoadedProject metadata, без файловых guards.
Owner готовит ProjectState с точным saved cell через constructor (revision = 0),
новой runtime identity, прежним ProjectId и новым пустым QUndoStack. Все allocations
выполняются до final applicability check; noexcept gate обменивает единственного
владельца ProjectSession и фиксирует Accept. Context epoch растёт, verification
products инвалидируются; notification видит согласованные state/history/baseline.
Cancel, изменение текущих входов, Close, shutdown или stale callback отзывают
публикацию. Старый проект и история сохраняются при failure/discard. Один worker
остаётся Busy до native completion/join. Save permission/receipt не меняются.

SavedProject восстанавливает published snapshot/path/digest, content и physical
binding. Наблюдаемая DatasetFileIdentity optional: у недоступного/непроверенного
файла нет фиктивной identity. Dirty по-прежнему сравнивает persistent content;
обычный Open clean, cell → dirty, Undo к baseline → clean. Open снимает прежний
Uncertain только восстановлением фактически прочитанного manifest, независимо от
того, состоялся ли тот Save. После доступного Open обычный Save переиспользует cache.

`recheckPointCache(ResourceLimits)` явно запускает тот же ограниченный probe в worker
по ожидаемому пути и descriptor. Успех атомарно обновляет availability и наблюдаемую
file identity внутри нового immutable SavedProject, сохраняя published content,
snapshotId/digest, runtime session, revision, параметры, history и dirty. Неверный
CacheId не принимается. Recheck failure/cancel оставляет прежние наблюдения; обнаруженные
missing/corrupt/access failures публикуют соответствующую availability без потери metadata.
Для импортированного ещё не сохранённого проекта recheck возвращает UnsafeState;
для Uncertain требуется Open, а не переинтерпретация prepared snapshot.

У недоступного cache C++ запрещает cell/Undo/Redo, Save/Save As и текущую verification
операцию. Close, подтверждённые Import/Open и recheck остаются доступны. Это guards
конкретных нынешних операций, не глобальный запрет будущего редактирования независимых
PNG/Rough datasets. Availability — наблюдение, а не вечная гарантия filesystem:
после удаления файла прежний флаг остаётся до recheck; Save повторяет path/identity/
envelope checks в worker и отказывает, сохраняя manifest. Изменение cell не делает I/O.
Будущие потребители обязаны повторять собственные проверки непосредственно перед I/O.

Полная integrity validation — отдельный явный C++ контракт `CacheReader::open` →
`validate(limits, temporaryParent, cancel, context)` вне GUI thread. Она требует
собственного resource budget, cancellation и applicability; controller-команда и
GUI полной validation в 05.3 не добавлены, никаких неявных вызовов нет.
Границы resolver/TOCTOU, cooperative access и conservative retention сохраняются.
Проверки и ограничения — [отчёт 05.3](reports/task-05/open-implementation.md).

## 29. Пути к данным

Для project-owned datasets manifest v1 хранит относительные пути от каталога проекта.
Проверяются absolute/UNC/drive-relative paths, traversal, Windows device names, ADS,
неоднозначные components и Unicode. Отдельный resolver проверяет существующие parents
и конечный файл через Win32 attributes и отклоняет все descendant reparse points,
включая junction. Отсутствующий leaf допустим. Перенос всего project directory
сохраняет references. Полный контракт и ограничения —
[project-manifest-format.md](project-manifest-format.md#storage-пути-и-retention).

Filesystem validation не является handle lease и не устраняет TOCTOU. Будущие файловые
операции повторяют проверки непосредственно перед использованием и соблюдают
протокол подготовки/публикации. Полная защита от внешнего изменения файлов не обещается.

Исходный ASC/XYZ может храниться как внешняя ссылка.

Недоступность исходного файла после успешного создания point cache не должна блокировать открытие проекта.

Если обязательный project-owned cache отсутствует или повреждён, проект должен открыть настолько доступное состояние, насколько это безопасно, и явно сообщить о недоступных операциях. Это восстановление ранее сохранённого проекта в задаче 05, а не создание нового пустого проекта; правило создания после успешного импорта (§13) его не запрещает.

## 31. Autosave и Recovery

Autosave должен быть отдельным от последнего явного пользовательского сохранения.

Схема:

```text
Explicit saved state
        +
Recovery/autosave state
```

Autosave не должен без необходимости перезаписывать последнее корректное explicit save.

Опубликованный autosave/recovery state должен ссылаться только на полностью записанные согласованные datasets. Неудачная запись не уничтожает предыдущее корректное сохранённое состояние (§28). Конкретный протокол устойчивой к прерыванию записи остаётся реализационным решением.

После аварийного завершения программа должна иметь возможность обнаружить recovery state и предложить пользователю восстановление.

Точная периодичность autosave является настройкой реализации, а не архитектурным контрактом.

### 31.1. C++ Autosave / Recovery (05.4)

`ProjectController::autosave()` использует тот же OperationRunner. Триггеры:
успешный Import/Save после native join и QTimer (начальный интервал 60 секунд).
При Busy попытка пропускается без очереди snapshots. Явная операция отзывает
pending Autosave и возвращает Busy до native completion; caller повторяет её после
освобождения worker. После irrevocable Accept необходимо дождаться receipt.
Cell/Undo/Redo не инвалидируют snapshot; более поздние правки сохраняются в state.
Отсутствие изменений определяется `matchesSavedContent`, а не runtime revision;
смена explicit baseline/path также требует обновить recovery. Dirty, baseline,
domain binding и история не меняются. Сохраняется только применённое domain state.

Storage — `AppLocalDataLocation/projects/recovery/<session UUID>.pc2drecovery`.
Переопределённый C++ storage root изолирует и recovery. Отдельный recovery v1 envelope
содержит checksum, lifecycle, snapshot и physical dataset reference, optional explicit
baseline с exact digest/path. Snapshots используют прежний manifest codec с точным
binary64; форматы `.pc2dproj` и Point Cache v1 не изменены. Physical reference хранится
отдельно, поскольку до первого Save cache расположен в принятом import storage.
По умолчанию recovery ограничен 12 MiB, discovery — 1024 записями и 64 MiB metadata
admission (включая прочитанные explicit baselines), каждый manifest —
прежними 4 MiB/4096 tokens/depth 32. Это admission budgets metadata, не размер облака.

Worker готовит QSaveFile с direct-write fallback=false, выполняет write/flush и ждёт
Ready permission. Controller проверяет OperationId/context epoch/runtime identity;
после Accept worker делает atomic commit. Только persisted receipt становится
последним recovery controller. Кооперативный QLockFile, expected digest и удержание
каталога native handle защищают публикацию; failure/cancel до commit сохраняют
предыдущую запись. Cleanup failure после commit — warning, опубликованное сохраняется.

`discoverRecovery()` читает только bounded metadata в worker, не меняя текущий проект
или файлы. Active определяется эксклюзивным Windows kernel event с session UUID
(Global namespace). RecoveryLease удерживается worker/controller, исчезает при
crash, закрытие HANDLE не требует файлового I/O. Timestamps не доказывают актуальность.
Различаются Active/Interrupted/Closed/Rejected/Invalid; отдельно —
Unsaved/MatchesExplicit/Modified/Conflict/Unknown по content и exact baseline digest.
Недоступный/изменившийся explicit save обрабатывается консервативно как Conflict.

`restoreRecovery(RecoveryRequest)` повторно проверяет record/digest/paths, захватывает
marker и переиспользует bounded cache probe и atomic owner exchange из Open.
ProjectId/cell/metadata сохраняются; runtime identity новая, Undo/Redo пусты. Прежний
проект сохраняется до Accept; confirmation/context/cancellation/reentry guards те же,
что у Open. Partial availability и запрет зависимых операций сохраняются; recovered
unsaved допускает явный bounded recheck без создания saved baseline. Closed candidate
до Ready атомарно маркируется Open с тем же state/references: авария сразу после
Accept обнаружима. Отмена последующего Accept может оставить консервативный Interrupted
(незавершённая попытка восстановления), сохраняя целый candidate. Source recovery
удерживается до следующего Autosave. При конфликте baseline отсоединён,
`recoveryRequiresSaveAs()` запрещает обычный Save; независимый explicit save не меняется.

`rejectRecovery(candidate)` фиксирует Rejected через permission/receipt; при ошибке
candidate сохраняется. `closeProject(discardConfirmed=false)` и
`requestShutdown(discardConfirmed=false)` сохраняют recovery. Только явный `true`
фиксирует подтверждённый Discard. При Close/замене/shutdown lifecycle metadata
маркируется Closed/Rejected в том же worker после завершения предыдущей операции.
Shutdown Ready ждёт и этот worker; destructor fallback drain не требует GUI callbacks.
Это ограниченный lifecycle I/O, не отменяемый общим shutdown cancellation. Ошибка
маркировки сохраняет recovery и может оставить Interrupted. Низкоуровневый shutdown
сохраняет последний опубликованный snapshot, не делает принудительного Save правок.
GUI Save/Discard/Cancel и предложение восстановления относятся к 05.5.

Autosave/discovery не открывают source/cache; restore/recheck читают только bounded
envelope/root (73 728 bytes непустого cache v1, ноль point pages). Copy, scanAll,
validate, импорт, PNG/reduced rebuild и geometry не вызываются. Accepted datasets
сохраняются на диске независимо от shared_ptr/процесса; recovery фиксирует их ссылки,
но не доказывает ownership для удаления. GC/scavenger не добавлены. Гарантии относятся
к process crashes и обычным filesystem failures, не к физической потере питания,
некооперативной подмене файлов или общему recovery root на разных компьютерах.
Схема, проверки и ограничения — [отчёт 05.4](reports/task-05/autosave-recovery.md).

## 38. DXF Export

DXF exporter получает только финальную domain geometry.

Схема:

```text
PreciseGeometry
       ↓
DXF Exporter
       ↓
DXF
```

Exporter не выполняет fitting и не извлекает геометрию из QML. Предупреждение о неприменённых precise-изменениях и решение продолжить экспорт относятся к application layer (§23).

CircularArc → ARC

## 41. Управление памятью

Базовые правила:

1. Source cloud не загружается целиком в RAM.
2. Large datasets читаются потоково или блоками.
3. Point cache поддерживает выборочный доступ.
4. Reduced cloud может храниться в RAM только если его фактический размер это позволяет.
5. Временные большие буферы должны иметь явное ограниченное время жизни.
6. QML не должен получать копии многомиллионных массивов точек в форме отдельных объектов.
7. Передача больших данных между слоями должна избегать лишнего копирования.

До создания крупных datasets проверяются представимость размеров, arithmetic overflow, допустимость конечных параметров и потребность в ресурсах. Недоступность памяти или других ресурсов приводит к структурированному failure без публикации частичного dataset и разрушения текущего корректного результата.

Хранение всех версий на диске не требует одновременной загрузки всех PNG в RAM. Освобождение runtime-буферов не удаляет сохранённые версии; Undo работает без полных копий тяжёлых datasets (§27).

Конкретные размеры буферов и ресурсная стратегия определяются реализацией и профилированием; универсальный RAM-limit не задаётся.

## 42. Производительность

Архитектура не должна жертвовать корректностью и удобством пользователя ради микроскопических оптимизаций.

Оптимизация выполняется по измерениям.

Приоритет:

```text
1. Корректность.
2. Сохранность данных.
3. Предсказуемое использование RAM.
4. Отзывчивый интерфейс.
5. Эффективный disk/network I/O.
6. Скорость вычислений.
7. Микрооптимизации.
```

UI может использовать немного больше ресурсов, если это даёт существенное улучшение удобства и визуального качества.

Для тяжёлых вычислительных подсистем производительность остаётся существенным требованием.

## 43. Тестируемость

Основные вычислительные подсистемы должны тестироваться без запуска полноценного GUI.

Как минимум отдельно тестируемыми должны быть:

```text
ASC/XYZ parsing
coordinate conversion
cache read/write
cache version validation
project serialization
geometry model
topology validation
raster operations
reduced-cloud extraction
precise algorithms
one-sided tolerance validation
DXF export
```

QML не должен быть обязательной частью unit tests вычислительного ядра.

Вспомогательный Synthetic Point Cloud Generator отделён от production application: Geometry JSON + Scan Scenario JSON → XYZ/ASC + manifest. Его канонический контракт — [отдельная спецификация](tools/synthetic-cloud-generator.md); DXF parsing и NX import не требуются. CADContour2D в обычном synthetic тесте получает только облако, без ground-truth подсказок и требований автоматического defect detection.

## 44. Безопасность пользовательских данных

Операции, изменяющие большие persistent datasets, должны по возможности использовать безопасную схему записи.

Исходный persistent point cache не должен разрушаться из-за ручного редактирования.

Перестроение вычисляемого результата не должно удалять предыдущее корректное состояние до успешного завершения новой операции, если это требуется для безопасного восстановления или Undo.

Project save и autosave соблюдают инварианты согласованной публикации (§§28, 31). Подтверждённый межэтапный reset является отдельным намеренным изменением состояния без Undo, а не неудачным пересчётом.

Reset убирает второй этап из текущего project state, но не требует немедленного удаления файлов, на которые ссылается последнее корректное сохранение. Очистка временных и иных неиспользуемых данных определяется реализацией; она не распространяется на сохранённые версии Density Map. Автоматического удаления старых версий или ограничения их количества нет (§15).

## 45. Указатель основных Open decisions

Это краткий указатель основных инженерных вопросов, а не исчерпывающий перечень всех деталей реализации.

Point Cache Format и Spatial Index для v1 определены в §§12–14 и
[point-cache-format.md](point-cache-format.md) по результатам задачи 03.
Compression не требуется для v1; возможное дальнейшее развитие формата не
блокирует следующие этапы.

- **Density Map Versions:** политика повторного построения с теми же параметрами, представление идентичности/provenance и связей datasets, persistence layout и UI переключения; обязательные контракты — §§9, 15, 23, 27–28. Автоматическое восстановление Precise Stage не утверждено (§6.2).
- **Density PNG Encoding:** bit depth и mapping — [algorithms.md, §6](algorithms.md#6-построение-density-map); хранение metadata — §15.
- **Project Persistence:** UTF-8 JSON manifest v1 и metadata foundation реализованы в 05.1 (§28); Save/Save As и atomic publication — в 05.2 (§28.1), Open/partial availability — в 05.3 (§28.2), C++ Autosave/Recovery — в 05.4 (§31.1). GUI workflow — 05.5.
- **Reduced Cloud Storage:** RAM, project-owned dataset или восстановление из cache (§18), обязательно с сохранением ручных удалений.
- **Autosave/Recovery:** C++ storage/triggers/publication/lifecycle определены в §31.1; GUI-предложение восстановления и Save/Discard/Cancel — 05.5.
- **Worker applicability:** механизм обеспечения инварианта §25.
- **Precise methods:** локальные Open decision в [algorithms.md](algorithms.md#45-указатель-основных-open-decisions).
- **DXF Version / NX Compatibility:** §38; окончательное решение после реальной проверки в целевом окружении.

## 46. Решения, которые не должны приниматься локально без изменения архитектуры

Следующие изменения считаются архитектурными и требуют осознанного пересмотра этого документа:

- замена C++ как языка вычислительного ядра;
- замена Qt Quick/QML как основного GUI;
- перенос основной бизнес-логики в QML/JavaScript;
- отказ от persistent point cache;
- объединение rough и precise stages;
- использование PNG как источника финальной точной геометрии;
- изменение модели fixed user geometry;
- автоматический запуск тяжёлых пересчётов;
- хранение domain geometry только в GUI;
- изменение модели одностороннего допуска;
- отказ от непрерывности финальных контуров;
- превращение `.pc2dproj` в обязательный гигабайтный монолит без отдельного архитектурного решения.

## 47. Итоговая архитектурная схема

```text
                    ┌─────────────────────────┐
                    │       Qt Quick/QML      │
                    │      Presentation       │
                    └────────────┬────────────┘
                                 │
                                 ▼
                    ┌─────────────────────────┐
                    │    Application Layer    │
                    │ operations / commands   │
                    └────────────┬────────────┘
                                 │
              ┌──────────────────┼──────────────────┐
              │                  │                  │
              ▼                  ▼                  ▼
       ┌────────────┐     ┌─────────────┐    ┌────────────┐
       │  Project   │     │  Geometry   │    │   Cache    │
       │   State    │     │    Model    │    │   Layer    │
       └──────┬─────┘     └──────┬──────┘    └─────┬──────┘
              │                  │                 │
              │          ┌───────┴────────┐        │
              │          │                │        │
              ▼          ▼                ▼        ▼
        ┌──────────┐ ┌──────────┐  ┌───────────┐ ┌──────────┐
        │ Raster   │ │Precise   │  │  Export   │ │ Point    │
        │ Stage    │ │Processing│  │   DXF     │ │  Cache   │
        └────┬─────┘ └────┬─────┘  └───────────┘ └──────────┘
             │            │
          OpenCV        Eigen /
                       geometry algorithms
```

Стрелки схемы показывают концептуальные связи компонентов и используемые ими средства, а не обязательный граф C++ dependencies. Ограничения зависимостей определены в §8.

Основной принцип системы:

> UI управляет процессом, application layer координирует операции, domain model хранит состояние и геометрию, а специализированные вычислительные подсистемы выполняют работу над данными, не становясь владельцами пользовательского интерфейса.
