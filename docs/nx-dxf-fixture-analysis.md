# Анализ DXF fixtures Siemens NX

Дата анализа: 2026-10-08. Исследованы фактические ASCII DXF из [tests/fixtures/dxf/nx](../tests/fixtures/dxf/nx/), включая HEADER, TABLES, BLOCKS, ENTITIES и OBJECTS. Код приложения, генератора и exporter не изменялся; fixtures не изменялись.

## Решение и границы вывода

Принятый пользователем контракт первой версии остаётся **LINE + ARC + CIRCLE** для итоговой domain geometry, автоматического построения, ручного редактирования, precise-stage, Geometry Optimization, DXF export и ground-truth эскиза генератора.

Контур — замкнутая последовательность LINE/ARC либо самостоятельный CIRCLE. Внешний и все внутренние контуры замкнуты; один DXF генератора описывает один внешний и `0..N` внутренних контуров.

**ELLIPSE не поддерживается в первой версии. Автоматическая аппроксимация ELLIPSE отрезками или круговыми дугами запрещена: она изменяет исходную геометрию.** SPLINE также не входит в первую версию. Различие входной DXF entity и внутреннего примитива не разрешает терять геометрию при чтении.

Текущие fixtures не подтверждают достаточность этого набора для чтения всех четырёх файлов: три содержат настоящую некруговую ELLIPSE-геометрию в DXF. Это основание подготовить новые эталоны из NX, а не расширять внутреннюю модель. По последующему указанию пользователя существующие спецификации пока оставлены без изменений; этот отчёт фиксирует результаты и принятое решение.

## Общие свойства файлов

- Во всех четырёх `$ACADVER = AC1018` (формат AutoCAD 2004), `$INSUNITS = 4` (миллиметры), `$MEASUREMENT = 1`, `$LUNITS = 2`. Масштаб не выводился из имён файлов или размеров. Значения version/units сверены с [Autodesk DXF HEADER reference](https://help.autodesk.com/cloudhelp/2024/ENU/AutoCAD-DXF/files/GUID-A85E8E67-27CD-4C59-BE61-4DC9FADBE74A.htm).
- В ENTITIES все координаты Z у LINE, POINT, центров и векторов полуосей ELLIPSE равны нулю. Нормали всех ELLIPSE — `(0, 0, 1)`; геометрия уже лежит в XY. `$ELEVATION` и `$PELEVATION` равны нулю, thickness у геометрии не задана.
- Ненулевые Z есть в служебных данных: например, `$EXTMIN.z = -0.5`, `$EXTMAX.z = 5.0`, направления VIEW/VPORT. Эти значения не означают неплоскую геометрию детали. HEADER extents не охватывают фактическую геометрию и не пригодны как её bounding box.
- Геометрия контуров находится на layer `1`, в model space (owner `1F`). В `arc`, `circle`, `rectangle` имеется одиночный POINT `(0, 0, 0)` на layer `61`, handle `77`. Он не является границей контура; его назначение в исходном NX не установлено. Объявлен также неиспользуемый геометрией layer `0`. В `model` объявлены только `0` и `1`.
- В каждом BLOCKS имеются три пустых служебных блока: `*Model_Space`, `*Paper_Space`, `*Paper_Space0` (по три BLOCK/ENDBLK). INSERT и геометрии внутри этих блоков нет; разворачивать пользовательские block instances не требуется.

Количество entities непосредственно в ENTITIES:

|---|---:|---:|---:|---:|---:|---:|---:|---:|

## Конкретные элементы и замкнутость

Handles ниже — значения group code `5` внутри соответствующего DXF. Они идентифицируют экспортированные entities, но не являются именами или идентификаторами исходных объектов эскиза NX. Ни исходных `.prt`, ни соответствия sketch objects этим handles в репозитории не обнаружено.

### rectangle.dxf

Четыре LINE (`79`, `7B`, `7C`, `7D`) образуют один замкнутый четырёхугольник; внутренние контуры отсутствуют. Все соседние endpoints точно совпадают в записанных десятичных координатах: зазоры LINE–LINE равны нулю. Отдельной contour entity или флага closed нет; замкнутость следует из соединения endpoints. Порядок записей ENTITIES не задаёт готовый обход контура.

В DXF это параллелограмм с углами около `41.753113°` и `138.246887°`, а не прямоугольник с прямыми углами. Имя файла не подтверждает сохранение исходной формы NX.

### circle.dxf

Единственная граница — полный ELLIPSE, handle `79`, центр `(0, 0)`, полуоси приблизительно `69.524885866` и `26.100963127` мм. Group `40 = 0.375419`, диапазон параметров groups `41/42 = 0 .. 6.283185307179586` (`2π`), что задаёт замкнутый полный эллипс без сборки endpoints.

Этот объект соответствует единственной внешней границе в данном DXF. Установить, был ли он окружностью в исходном NX, по этому файлу нельзя. CIRCLE в файле нет.

### arc.dxf

Две ELLIPSE являются открытыми эллиптическими дугами с общим центром `(16.716548, 8.482087)`, общей ориентацией полуосей и диапазоном параметров `2.747208169014265 .. 4.819554288183734` радиан:

| Handle | Полуось a, мм | Полуось b, мм | Роль по геометрическому расположению |
|---|---:|---:|---|
| `80` | 34.433398021 | 12.926951852 | Дуговая часть меньшего, внутреннего контура вместе с LINE `79`, `7B`, `7C` |
| `81` | 64.433398021 | 24.189521852 | Дуговая часть большего, внешнего контура вместе с LINE `7E`, `7D`, `7F` |

Оба отношения полуосей равны `0.375419`. Внешний и внутренний контуры представлены отдельными LINE и ELLIPSE; ARC, POLYLINE и флага closed нет.

LINE–LINE endpoints внутри каждой цепочки совпадают точно. Endpoints эллиптических дуг, рассчитанные по записанным параметрам, не совпадают точно с окончаниями LINE:

| Соединение | Зазор, мм |
|---|---:|
| ELLIPSE `80`, начало — LINE `79`, начало | 0.000003062503 |
| ELLIPSE `80`, конец — LINE `7C`, конец | 0.000008304160 |
| ELLIPSE `81`, начало — LINE `7E`, начало | 0.000005190101 |
| ELLIPSE `81`, конец — LINE `7F`, конец | 0.000014378220 |

Это две геометрически узнаваемые петли с численными зазорами, а не доказанная точная C0-замкнутость записанных entities. Возможное округление координат/отношения полуосей при экспорте объясняет порядок величины зазоров, но не устанавливает их причину. Значения не назначают универсальный endpoint tolerance и не разрешают автоматическое исправление DXF.

### model.dxf

Двенадцать LINE образуют три отдельные точно замкнутые четырёхугольные петли:

- внешний контур: `7E`, `7F`, `83`, `82`;
- внутренний контур: `77`, `7D`, `7C`, `79`;

Все зазоры LINE–LINE равны нулю в записанных координатах. Четыре самостоятельных полных ELLIPSE находятся внутри внешнего контура, вне двух внутренних четырёхугольников:

## Что означает ELLIPSE в этих файлах

По [Autodesk ELLIPSE reference](https://help.autodesk.com/cloudhelp/2023/ENU/AutoCAD-DXF/files/GUID-107CB04F-AD4D-4D2F-8EC9-AC90888063AB.htm), group `40` — отношение малой полуоси к большой, `11/21/31` — вектор большой полуоси относительно центра, `41/42` — параметры начала/конца. Для всех семи объектов `b/a = 0.375419`, существенно отличающееся от единицы. Поэтому это некруговые эллипсы/эллиптические дуги в содержимом DXF, а не точные окружности, просто записанные другим entity type.

Для проверки endpoints использована параметризация:

```text
A = вектор большой полуоси
N = единичная нормаль (0, 0, 1)
B = (b/a) * (N × A)
P(t) = C + A*cos(t) + B*sin(t)
```

Точное представление этих кривых конечным набором LINE/ARC/CIRCLE невозможно. Приближённая замена или обратное неравномерное масштабирование изменяют прочитанную геометрию и не входят в разрешённое поведение первой версии.

### Гипотеза о способе экспорта NX

Факты, поддерживающие гипотезу о плоском экспорте наклонной проекции исходного эскиза:

1. Во всех семи ELLIPSE одинаковое `b/a = 0.375419`; большие полуоси направлены практически вдоль X (в `model` Y-компоненты порядка `10^-16` мм).
2. Во всех четырёх файлах TABLES/VIEW содержит вид `Trimetric` с направлением `(0.7188730927569433, -0.5850486126764433, 0.3754192287502549)`. Его Z-компонента совпадает с отношением полуосей с точностью округления до шести знаков. Значение направления интерпретируется по [Autodesk VIEW reference](https://help.autodesk.com/cloudhelp/2023/ENU/AutoCAD-DXF/files/GUID-CF3094AB-ECA9-43C1-8075-7791AC84F97C.htm).
3. Ортогональная проекция окружности из XY на плоскость с единичной нормалью N имеет отношение полуосей `abs(N.z)`. Это математически согласуется с найденными параметрами.
4. Диагностический расчёт для `rectangle`: после деления только Y-координат на `0.375419` угол соседних сторон становится приблизительно `89.9999658°`. Такое общее сжатие согласуется с проекцией; файл при расчёте не изменялся.

**Это гипотеза, а не установленный факт об исходной геометрии NX.** Сохранённый именованный VIEW не доказывает, что он использовался для экспорта. В текущих DXF активный VPORT уже имеет направление `(0, 0, 1)`, UCS совпадает с мировой системой, ELLIPSE лежат в XY. Изменение вида при чтении не восстановит окружности. Тот же DXF мог быть получен из исходных эллипсов или после другого преобразования.

Файлы не содержат доступного соответствия между entities и исходными sketch objects NX; поиск исходных `.prt` и сведений о параметрах экспорта в репозитории результата не дал. Для `circle/79`, `arc/80–81`, `model/84–87` исходный тип объекта NX остаётся неподтверждённым. Общая наиболее согласованная с числами гипотеза — проекция окружности, двух круговых дуг и четырёх круглых внутренних границ соответственно.

## Достаточность LINE/ARC/CIRCLE

1. **Для всех текущих DXF без потери геометрии — недостаточно.** Геометрия `rectangle` состоит только из LINE; `circle`, `arc`, `model` требуют некруговую ELLIPSE для точного воспроизведения их текущего содержимого.
2. Для чтения именно этих трёх файлов понадобилась бы обработка ELLIPSE как геометрии, а не только как контейнера. Эта поддержка не добавляется: файлы считаются несовместимыми с первой версией. Одиночный POINT и служебные записи должны быть отличены от границ; они не обосновывают дополнительные внутренние примитивы или реализацию полного DXF standard.
3. Без потерь преобразовать найденные ELLIPSE в LINE/ARC/CIRCLE нельзя. POLYLINE/LWPOLYLINE и SPLINE не встретились; необходимость их чтения этими fixtures не подтверждена.
4. Причины расширять внутреннюю модель сейчас нет. Принятое решение сохраняется; подтверждение NX compatibility откладывается до новых подходящих fixtures.

Полной окружности в виде CIRCLE и смешанного контура LINE/ARC в данной выборке нет. Эти файлы показывают полный ELLIPSE и цепочки LINE/эллиптическая дуга; обобщать это на все режимы экспорта NX нельзя. Версия будущего exporter и успешный импорт его результата в NX также не подтверждаются анализом входных файлов.

## Проверки и неизменность fixtures

Фактически выполнены разбор всех DXF group-code/value пар, подсчёт records по секциям, проверка units/layers/blocks/Z, восстановление LINE-петель, расчёт полуосей и endpoints ELLIPSE, зазоров ближайших соседних endpoints, расположения четырёх полных эллипсов относительно LINE-контуров `model`. Это анализ fixtures, не тестирование реализованного DXF reader и не полный topology validator.

## Открытые вопросы

- Были ли семь ELLIPSE исходными эллипсами NX или результатом экспорта проекции? Нужны исходные sketch objects и параметры экспорта; DXF не позволяет однозначно восстановить это происхождение.
- Как NX экспортирует исходные окружности и круговые дуги без искажения формы в выбранном пользователем режиме? Новые fixtures должны реально содержать CIRCLE и ARC и позволить проверить endpoints смешанных LINE/ARC-контуров.
- Какую численную точность имеют endpoints в новых корректных DXF и как различать округление и реальный разрыв без молчаливого исправления ground truth? Из текущих эллиптических зазоров такой контракт не следует.
